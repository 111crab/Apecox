# 双视角初版启动小贴士

## 结论

第一人称与第三人称动画系统，不应该理解成“让两套动画逐帧同步”，而应该理解成：

> **共享同一套 Gameplay 状态与动作事件，第一人称（FP）和第三人称（TP）分别负责各自的视觉表现。**

核心原则：

```text
Gameplay / GAS / Weapon
        ↓
统一的角色动作语义
        ↓
 ┌───────────────┐
 │               │
FP Animation    TP Animation
本地视角表现      世界空间表现
```

例如角色执行 `Reload`：

```text
GA_Reload
   ↓
State.Reloading
   ↓
Action.Reload
   ├─ FP：播放第一人称换弹 Montage
   └─ TP：播放第三人称换弹 Montage
```

两套动画不需要是同一条 Animation Sequence，也不需要逐帧一致，只需要表达**同一个 Gameplay 行为**。

---

## 1. 角色 Mesh 结构建议

第一版推荐使用两套 Mesh：

```text
Character
│
├─ Capsule
│
├─ Mesh_TP
│   └─ 完整第三人称角色
│
├─ Camera
│
└─ Mesh_FP
    └─ 第一人称手臂
```

可见性通常这样组织：

```text
Mesh_FP
→ Only Owner See

Mesh_TP
→ Owner No See
```

结果：

- 本地玩家看到 FP Arms / FP Weapon。
- 其他客户端看到 TP Full Body / TP Weapon。

第三人称 Mesh 更适合作为角色的**世界空间真实表现**；第一人称手臂则更像一个 ViewModel。

---

## 2. Gameplay 状态只能有一个权威来源

不要让 `ABP_FP` 和 `ABP_TP` 各自判断角色当前是不是：

```text
Reloading
Firing
Aiming
Sprinting
```

否则两套表现很容易慢慢产生状态分歧。

推荐：

```text
Character / Weapon / GAS
        ↓
   Gameplay State
        ↓
    ┌───────┴───────┐
    ↓               ↓
 ABP_FP           ABP_TP
```

共享的数据可能包括：

```text
bIsAiming
bIsReloading
bIsFiring
bIsSprinting
CurrentWeaponType
GroundSpeed
MovementDirection
bIsInAir
```

如果项目已经大量使用 GAS，也可以使用 GameplayTag 表达：

```text
State.Weapon.Aiming
State.Weapon.Reloading
State.Weapon.Firing
State.Movement.Sprinting
```

FP / TP AnimBP 都只读取状态，而不是各自重新推导 Gameplay 真相。

---

## 3. Locomotion 不需要“同步动画”

移动状态应该共享，但动画实现可以完全不同。

例如：

```text
                 CharacterMovement
                        ↓
                 Velocity / State
                   ↙           ↘
              ABP_FP           ABP_TP
                ↓                ↓
         FP Arms Movement   TP Locomotion
```

FP 可能只有：

```text
Idle Arms
Walk Bob
Run Arms
Sprint
```

TP 则可能有：

```text
Idle
Jog
Run
Strafe
Jump
Land
Turn
```

只要两者都表达角色“正在移动 / 冲刺 / 跳跃”，就不需要播放同一条动画。

---

## 4. 真正需要同步的是“一次性 Gameplay Action”

重点包括：

```text
Fire
Reload
Equip
Unequip
Melee
Skill
Inspect
```

推荐从 Gameplay 层统一发起：

```text
Input Reload
      ↓
GA_Reload
      ↓
检查是否允许 Reload
      ↓
进入 Reload 状态
      ↓
触发 Action.Reload
       ├───────────┐
       ↓           ↓
FP Reload       TP Reload
Montage         Montage
```

因此建议建立一个“动作语义层”，例如：

```text
Action.Weapon.Fire
Action.Weapon.Reload
Action.Weapon.Equip
Action.Weapon.Melee
```

然后由 FP / TP 分别解析为自己的动画表现。

---

## 5. 不建议把 FP / TP Montage 全部写死在 Character 里

不推荐逐渐堆成：

```cpp
FPReloadMontage
TPReloadMontage

FPFireMontage
TPFireMontage

FPMeleeMontage
TPMeleeMontage
```

武器和动作数量增加后会迅速失控。

更适合做一个 Animation Set / DataAsset：

```text
DA_Rifle_AnimationSet

Actions
├─ Fire
│   ├─ FP Montage
│   └─ TP Montage
│
├─ Reload
│   ├─ FP Montage
│   └─ TP Montage
│
├─ Equip
│   ├─ FP Montage
│   └─ TP Montage
│
└─ Melee
    ├─ FP Montage
    └─ TP Montage
```

甚至可以通过 GameplayTag 查询：

```text
Action.Weapon.Fire
        ↓
AnimSet->FindAnimation(ActionTag)
        ↓
得到 FP Montage + TP Montage
```

这样更加适合 GAS + DataAsset 的项目结构。

---

## 6. FP 和 TP 动画时长不需要完全一致

例如：

```text
FP Reload = 1.65s
TP Reload = 1.90s
```

不应该为了“同步”强制让两条动画完全等长。

更合理的做法是把 Reload 当成一个 Gameplay 行为：

```text
Reload Ability

Start
↓
Magazine Remove
↓
Magazine Insert
↓
Reload Complete
```

FP / TP 可以各自围绕这些关键阶段表现。

也就是说：

> **Gameplay Timeline 是逻辑真相，Animation Timeline 是视觉表现。**

---

## 7. 最重要的坑：Gameplay Notify 不能执行两次

如果 FP 和 TP Montage 都包含：

```text
Notify：InsertMagazine
```

而这个 Notify 会真正修改 Ammo：

```text
FP Notify → Ammo +30
TP Notify → Ammo +30
```

就会发生重复 Gameplay。

因此必须区分：

### Gameplay 事件

只能存在一个权威执行来源：

```text
Consume Ammo
Reload Commit
Spawn Projectile
Apply Damage
Modify Attribute
```

### Presentation 事件

FP / TP 可以分别执行：

```text
Magazine Sound
Bolt Sound
Muzzle Flash
Shell Ejection
Camera Recoil
Third Person Muzzle FX
```

原则：

> **Gameplay 只执行一次，Presentation 可以多视角分别表现。**

---

## 8. GAS 可以作为动作总指挥

如果项目已经使用 GAS，推荐让 Ability 决定动作生命周期。

以 `GA_Reload` 为例：

```text
ActivateAbility
     ↓
检查 Ammo / Gameplay State
     ↓
Commit Ability
     ↓
添加 State.Reloading
     ↓
启动 Reload Action
     ↓
FP Reload Presentation
+
TP Reload Presentation
     ↓
到达 Gameplay Reload Point
     ↓
修改 Ammo
     ↓
EndAbility
     ↓
移除 State.Reloading
```

避免出现：

```text
FP Montage 自己控制一套 Reload
TP Montage 又控制一套 Reload
Weapon Component 再维护第三套状态
```

这会让系统后期非常难维护。

---

## 9. 第三人称可以用 Lyra 动画，但不要为了动画序列搬整个 Lyra 框架

如果已经有 Lyra 的第三人称动作序列，可以直接作为 TP 动画资源使用。

但是要区分：

> Lyra 的最终动画效果，不等于几条 Animation Sequence 本身。

Lyra 的角色表现还包含：

```text
Locomotion
Animation Layers
Aim
Orientation
Movement State
UpperBody
Weapon Pose
```

对于当前 FPS 项目，更推荐：

```text
Lyra Animation Sequence
        ↓
自己的 TP AnimBP
```

先实现一个清晰、可解释的 TP AnimGraph，而不是把整套 Lyra Animation Framework 直接移植进来。

---

## 10. 第三人称 FPS 非常适合 Layered Blend

典型需求：

> 玩家下半身跑步，上半身继续持枪 / 开火。

推荐结构：

```text
Locomotion
    ↓
Save Cached Pose
    ├──────────────────┐
    ↓                  ↓
Base Pose         UpperBody Slot
    │                  │
    └──── Layered Blend Per Bone
                    ↓
                Final Pose
```

例如从：

```text
spine_01
```

开始进行上半身覆盖。

结果：

```text
下半身：
继续 Run / Strafe

上半身：
Fire / Reload / Aim
```

这非常适合第三人称枪械动画。

---

## 11. Fire、Reload 不一定都用同一种 Slot

一般来说：

### Fire

通常非常适合：

```text
UpperBody Montage
```

因为需要边移动边开枪。

### Reload

大多数枪械 Reload 也可以 UpperBody。

但如果动画包含：

```text
明显下蹲
全身重心变化
大幅身体转动
```

则可能更适合：

```text
FullBody Montage
```

因此不要把规则写死成：

> FPS 所有枪械动作都必须 UpperBody。

应该由动画本身决定。

---

## 12. Aim 是 FP / TP 差异最大的系统之一

第一人称中：

```text
Camera Direction
≈ Aim Direction
```

因此 FP 武器表现通常直接围绕 Camera 构建。

第三人称中：

```text
Camera Direction
≠ Character Forward
```

所以 TP 通常需要计算：

```text
Aim Pitch
Aim Yaw
```

常见关系：

```text
Control Rotation
-
Actor Rotation
=
Aim Offset
```

TP AnimBP 可以类似：

```text
Locomotion
↓
Weapon Pose
↓
Aim Offset
↓
IK
↓
Final Pose
```

否则会出现：

> 本地镜头朝上射击，但其他玩家看到你的枪依然水平向前。

---

## 13. 武器也建议区分 FP / TP 表现

推荐：

```text
WeaponActor

├─ Mesh_FP
│   └─ OnlyOwnerSee
│
└─ Mesh_TP
    └─ OwnerNoSee
```

FP：

```text
Attach → FP Arms WeaponSocket
```

TP：

```text
Attach → TP hand_r WeaponSocket
```

这样可以分别调整：

```text
FP Weapon
→ 为镜头构图服务

TP Weapon
→ 为世界空间正确性服务
```

两者不会互相妥协。

---

## 14. Root Motion 的世界移动权威不能来自 FP Arms

以后如果加入：

```text
Melee
Slide
Vault
特殊技能位移
```

不要让 FP Arms 的 Root Motion 驱动 Character。

错误思路：

```text
FP Arms Root Motion
→ Character World Movement
```

推荐：

```text
Character / CMC / TP Character Root
→ 决定世界位移

FP Arms
→ 只表现对应动作
```

可以把两者理解成：

```text
FP Arms
= ViewModel

TP Character
= World Character
```

这是整个双视角设计里非常重要的认知。

---

## 15. 多人同步时，应该同步 Gameplay，而不是 Pose

例如 Client A 开枪：

```text
Client A
按 Fire
```

本地可以立刻执行：

```text
FP Fire
Camera Recoil
Local Muzzle Flash
```

确保手感及时。

同时：

```text
Client A
↓
Ability / RPC
↓
Server
↓
验证 Fire
↓
同步 Gameplay State / Event
↓
Client B
↓
播放 Client A 的 TP Fire Animation
```

最终：

```text
Owner
→ 看到 FP Animation

Remote Client
→ 看到 TP Animation
```

但是这两者来自：

```text
同一次 Fire Gameplay Action
```

而不是把 FP Pose 复制给第三人称。

```text
                    Character
                        │
          ┌─────────────┴─────────────┐
          │                           │
    Gameplay / GAS              CharacterMovement
          │                           │
   Current Action                 Movement State
          │                           │
          └──────────────┬────────────┘
                         │
                 Shared Anim State
                         │
                ┌────────┴────────┐
                │                 │
             ABP_FP            ABP_TP
                │                 │
         First Person        Third Person
             Arms             Full Body
                │                 │
             FP Gun            TP Gun
```

一次动作：

```text
GA_Fire
   ↓
Action.Weapon.Fire
   ↓
AnimationSet
   ├─ FP Fire Montage
   └─ TP Fire Montage
```

## 17. 第一版推荐启动顺序

### 第一步：建立双 Mesh

完成：

```text
Mesh_FP
Mesh_TP
```

并设置：

```text
OnlyOwnerSee
OwnerNoSee
```

先确保本地 / 远端显示关系正确。

### 第二步：只完成 TP Locomotion

先只验证：

```text
Idle
Move
Run
Jump
```

可以直接使用已有 Lyra 动画序列。

这一步不要急着接 Fire / Reload。

### 第三步：加入 TP Aim + Fire

完成：

```text
Aim Offset
+
UpperBody Fire Montage
```

重点验证：

```text
边跑
+
瞄准
+
射击
```

第三人称姿势是否稳定。

### 第四步：统一 Action 驱动

让：

```text
GA_Fire
GA_Reload
GA_Equip
```

统一触发：

```text
Gameplay Action
        ↓
FP Presentation
+
TP Presentation
```

不要让两个 AnimBP 各自维护 Gameplay。

### 第五步：扩展 Reload / Equip / Skill

在 Fire 的架构跑通以后，再逐个接入：

```text
Reload
Equip
Melee
Skill
```

## 18. 最容易踩的坑

### 坑 1：把“同步”理解成播放同一条动画

错误目标：

> FP / TP 必须同帧、同 Sequence。

正确目标：

> FP / TP 必须表达同一个 Gameplay Action。

### 坑 2：两个 AnimBP 各有一套 Gameplay 状态判断

最终会导致：

```text
FP 认为正在 Reload
TP 认为已经结束
Gameplay 又认为还在 Reload
```

状态来源必须统一。

### 坑 3：两个 Montage 都能修改 Gameplay

会出现重复：

```text
Consume Ammo
Damage
Reload Commit
Projectile Spawn
```

Gameplay 必须有唯一权威。

### 坑 4：为了用 Lyra 动画搬整套 Lyra 系统

如果当前项目已经有自己的 Character / GAS 架构，只借用适合的动画资源和必要思路即可。

### 坑 5：FP Weapon 和 TP Weapon 强行共用同一 Transform

第一人称为了镜头表现经常需要特殊位置，第三人称则需要世界空间正确。

应该允许两套表现独立调整。

### 坑 6：FP Arms 决定世界移动

FP Arms 是视觉 ViewModel，不应该成为 Character 世界位移的权威。

### 坑 7：TP 只做动画，不做 Aim

如果 TP 没有 Aim Offset / Weapon Pose / IK，远端看到的持枪方向很容易明显错误。

---

## 19. 对当前 FPS 项目的意义

加入第三人称以后，这个项目不再只是：

> 第一人称 FPS Demo

而可以体现：

```text
Owner FP Presentation
+
Remote TP Presentation
+
GAS
+
Replication
+
Animation Layering
+
Aim / IK
+
Weapon Attachment
```

这会明显增强它作为 **UE Gameplay / Character 客户端项目** 的表达能力。

尤其可以展示：

```text
同一个 Gameplay Action
        ↓
根据观察者身份
        ↓
产生不同 Presentation
```

这是非常典型的客户端工程问题。

---

## 20. 最后记住一句话

> **第一人称和第三人称不是两套 Gameplay，而是同一套 Gameplay 的两套 Presentation。**

围绕这个原则组织：

```text
Fire
Reload
Weapon
Skill
Animation
Replication
```

后面的系统都会清晰很多。
