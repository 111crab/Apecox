# 后续动画组织建议

## 结论

当前第一人称 AnimBP **不需要推翻重做**。

从现有结构来看，它已经形成了比较清楚的 Pose Pipeline：

```text
Base Pose
↓
Locomotion Additive
↓
姿态 / Aim / Airborne 等状态叠加
↓
Animation Family
↓
Montage Slot
↓
Recoil / Procedural 修正
↓
Left Hand IK
↓
Final Pose
```

目前的问题不是“图太大”，而是已经到了需要控制后续扩张方式的阶段。

核心目标：

> **保留现在的 Pose Composition 思路，但不要继续让所有武器、所有状态都无限堆在同一个 AnimGraph 中。**

---

# 1. 当前结构值得保留的部分

## 1.1 Base Pose + Additive Locomotion

当前 Rifle 的组织方式大致是：

```text
Standing Base
├─ Rifle Idle Pose
└─ Rifle Crouched Idle Pose
        ↓
Blend Poses by Bool

Standing Locomotion
├─ Sprint Loop
└─ Rifle Movement BlendSpace
        ↓
Blend Poses by Bool

Standing Base
+
Standing Locomotion
↓
Apply Additive
↓
Standing Pose
```

这是一种很适合第一人称 Arms 的组织方式。

第一人称常见需求本身就是：

```text
持枪基础姿势
+
移动摆动
+
Aim
+
Lean
+
Recoil
+
IK
```

因此继续使用 **Pose Composition**，而不是把所有状态都塞进一个巨大 State Machine，是合理的。

---

# 2. Ground / Air / Aim 应继续保持“层”的概念

当前已有类似：

```text
Standing / Crouching / Prone
↓
Ground Pose
↓
Airborne Adjustment
↓
Aim Adjustment
```

后续应继续坚持：

> 一个层只负责一种明确的 Pose 语义。

例如：

```text
Base Pose
↓
Movement
↓
Ground / Air
↓
Aim
↓
Lean
↓
Weapon Family
↓
Montage
↓
Procedural
↓
IK
```

不要让某一块同时承担：

```text
移动
+
Reload
+
武器类型
+
Gameplay 状态
```

---

# 3. 继续使用 Bool Blend，但限制用途

当前使用：

```text
IsCrouching
IsSprinting
IsProne
IsFalling
IsAiming
```

这些作为简单、互斥的姿态选择是合理的。

适合：

```text
Standing / Crouching
Normal Move / Sprint
Hip Fire / Aim
Ground / Air
```

不适合未来继续扩展成：

```text
IsRifle
IsPistol
IsShotgun
IsSniper
IsReloading
IsEquipping
IsInspecting
IsMelee
...
```

当状态数量明显增加时，应考虑：

```text
Blend Poses by Enum
```

或者更进一步：

```text
Linked Anim Layer
```

---

# 4. Weapon Family 是下一阶段最值得模块化的部分

当前已经存在：

```text
AnimationFamily
├─ Rifle
└─ Unarmed
```

这是非常好的基础。

目前还可以继续维持。

但是如果未来增加：

```text
Pistol
Shotgun
SMG
Sniper
```

不要复制四套 Rifle Graph。

更推荐演进成：

```text
ABP_FP_Main
│
├─ Shared State
├─ Shared Overlay
├─ Montage Slot
├─ Recoil
├─ IK
│
└─ Weapon Animation Layer
       ├─ Rifle Layer
       ├─ Pistol Layer
       ├─ Shotgun Layer
       └─ Unarmed Layer
```

即：

> 主 AnimBP 负责公共管线，武器特有 Pose 交给独立 Animation Layer。

---

# 5. Linked Anim Layer 的使用时机

现在不必为了“架构高级”立刻重构。

建议只有在出现以下情况时再拆：

- 同类 Weapon Family 已经有 3 套以上；
- Rifle / Pistol / Shotgun 各自都出现大量重复节点；
- 修改公共逻辑时需要在多处分支同步修改；
- 主 AnimGraph 已经难以快速定位某个 Weapon 的动画链；
- 新增一把武器必须复制整个 Locomotion / Aim / Overlay 分支。

如果还没到这一步，保持现状即可。

---

# 6. Cached Pose 只在“确实复用”时使用

当前结构如果某个 Pose 会被多个分支使用，可以使用：

```text
Save Cached Pose
↓
Use Cached Pose
```

例如：

```text
Base Locomotion
↓
Save Cached Pose: FP_BasePose

Use → Aim
Use → Reload Layer
Use → Weapon Overlay
```

但不要为了形式上“像大型项目”而到处增加 Cached Pose。

判断标准：

> 这个 Pose 是否真的被多个后续分支反复读取？

如果只走一次，不需要强行缓存。

---

# 7. Additive 需要明确顺序

当前 AnimGraph 中已有大量：

```text
Apply Additive
Apply Mesh Space Additive
```

后续重点不是减少 Additive，而是明确顺序。

建议形成一套自己的约定，例如：

```text
Base Pose
↓
Locomotion Additive
↓
Aim / Weapon Additive
↓
Lean / Airborne Overlay
↓
Montage
↓
Recoil
↓
IK
```

实际项目可以调整，但要满足：

> 每一层为什么在前、为什么在后，自己能够解释。

尤其 `Mesh Space Additive` 对顺序比较敏感。

---

# 8. Montage 继续用于“一次性动作”

当前 Slot 放在持续 Pose 计算之后，这个方向是正确的。

推荐继续：

```text
State / Pose
→ 负责持续状态

Montage
→ 负责 Fire / Reload / Equip / Skill / Melee 等一次性动作
```

不要把：

```text
Reload
Fire
Equip
Skill
```

全部做成 State Machine State。

否则 Transition 很快失控。

---

# 9. IK 必须继续保持在最终修正层

当前链路大致是：

```text
Montage / Pose
↓
Transform Modify Bone
↓
FABRIK
↓
Output Pose
```

这种组织是合理的。

IK 适合放在较靠后的位置，因为它解决的是：

> 前面所有动画已经计算完成以后，手最终应该放在哪里。

但必须继续使用：

```text
LeftHandIKAlpha
```

控制 IK 是否参与。

例如：

```text
Normal Rifle Pose
→ LeftHandIKAlpha = 1

Reload
→ LeftHandIKAlpha → 0
```

否则 Reload 时左手会被 FABRIK 强制拉回枪械 IK 点。

---

# 10. Recoil 与 IK 的顺序需要保持可解释

当前：

```text
Pose
↓
Transform Modify Bone（Recoil）
↓
FABRIK
↓
Output
```

这种顺序的意义是：

```text
先改变武器 / 手臂整体 Recoil
↓
再让左手重新对齐最终武器位置
```

这通常比：

```text
先 IK
↓
再把武器整体推走
```

更容易保持握持稳定。

如果未来发现具体资产表现异常，再针对实际效果调整。

---

# 11. Event Graph 尽量只负责 Animation Data

理想职责：

```text
Get Owning Character
↓
读取 Gameplay / Movement 状态
↓
更新 Animation Variables
```

例如：

```text
Speed
Direction
IsFalling
IsAiming
IsSprinting
AnimationFamily
AimPitch
AimYaw
IK Alpha
```

不要让 Event Graph 负责：

```text
扣 Ammo
Apply Damage
决定能不能 Reload
激活 Ability
修改 Weapon Gameplay State
```

这些应该留在：

```text
Character
Weapon
GAS
Gameplay Component
```

AnimBP 负责：

> 已知当前状态以后，算出应该显示什么 Pose。

---

# 12. 第三人称不要塞进当前 FP AnimBP

加入 TP 时推荐：

```text
Shared Gameplay State
       ↓
   ┌───┴───┐
   ↓       ↓
ABP_FP    ABP_TP
```

FP：

```text
ViewModel / Arms
```

TP：

```text
World Character / Full Body
```

共享：

```text
Fire
Reload
Aim
Sprint
WeaponType
GameplayTag
Movement State
```

不共享：

```text
最终 Pose
具体 Animation Sequence
FP / TP Montage Asset
IK 方案
Aim 表现
```

核心原则：

> **共享 Gameplay，不共享最终 Pose。**

---

# 13. Lyra TP 动画的使用建议

可以使用 Lyra 的 Animation Sequence。

但不建议为了使用这些 Sequence，把整套 Lyra Animation Framework 搬进现有项目。

推荐：

```text
Lyra Animation Sequence
↓
自己的 ABP_TP
```

先实现：

```text
Idle
Move
Run
Jump
Aim
Fire UpperBody
Reload
```

如果后续确实需要，再研究 Lyra 中的：

```text
Animation Layer
Orientation
Turn
Aim
Locomotion
```

---

# 14. 后续重构的硬判断标准

当前阶段不建议大改。

只有当出现下面问题时，再考虑重构：

1. 新增一个 Weapon 需要复制大量现有节点；
2. 同一 Pose 逻辑在 3 个以上位置重复；
3. 找一个动画状态需要在图里翻很久；
4. 修改公共逻辑经常漏改某个 Weapon 分支；
5. Animation Family 已经从 2 个增长到 4～5 个；
6. Event Graph 开始承担 Gameplay 决策；
7. Montage、IK、Additive 之间频繁出现互相打架。

在此之前：

> **可解释、可运行、可快速定位，比“架构形式更高级”重要。**

---

# 15. 当前阶段最推荐做的整理

只做轻量整理：

- 统一 Comment Box 命名；
- 明确每个区域职责；
- 统一变量命名；
- 删除失效或废弃节点；
- 对明显重复 Pose 使用 Cached Pose；
- 保留 AnimationFamily；
- TP 建独立 AnimBP；
- 不在秋招前进行大规模 Linked Anim Layer 重构；
- 新 Weapon 再决定是否拆 Layer。

---

# 16. 推荐最终 Pose Pipeline

可以把当前系统抽象成：

```text
Gameplay / Movement Data
        ↓
Base Weapon Pose
        ↓
Locomotion Additive
        ↓
Ground / Air State
        ↓
Aim / Lean / Overlay
        ↓
Animation Family
        ↓
Montage Slot
        ↓
Weapon Recoil
        ↓
Left Hand IK
        ↓
Final Pose
```

这条链以后应作为整个 FP Animation System 的主心骨。

---

# 最后原则

> **复杂但有清晰 Pose Pipeline，是正常的。**

> **真正需要避免的，是新功能不断通过复制节点和新增 Bool 分支横向堆积。**

当前系统的首要任务不是重写，而是：

```text
理解
↓
命名
↓
整理
↓
限制扩张
↓
在真正需要时模块化
```
