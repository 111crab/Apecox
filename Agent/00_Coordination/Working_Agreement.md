# Apecox 协作约定

更新日期：2026-09-19

## 角色分工

- 用户：确认方向、审核公开命名和设计、执行需要视觉判断的 UE 编辑器操作、完成最终 PIE 体验验证。
- Codex 主代理：高层规划、架构研究、维护当前阶段、直接调度子代理、实施或集成代码、审查产出、给出人工操作与验证标准、收口 Git。
- Codex 子代理：只执行主代理分配的边界明确任务，直接返回实现或审查结果，不要求用户中转 Prompt。

## 默认工作流

- 先讨论清楚目标、职责边界、公开命名和验证范围。
- 决策成立后更新 `Current_Phase.md`；没有决定性结论时不产生额外文档。
- 涉及新 C++ 设计时，先覆盖 `Current_Code_Design.md` 给用户审阅。
- 用户批准后由 Codex 主代理直接创建并管理子代理，不再要求用户复制 Prompt 到 Claude Code 或新建子代理窗口。
- 子代理实施或审查，主代理负责检查代码、命名、GAS/网络生命周期和任务范围并完成集成。
- 用户确认公开设计后自行刷新 Rider 项目文件；Codex 不在讨论中频繁生成解决方案。
- Codex 覆盖 `Current_UE_Manual_Steps.md`，用户按步骤配置 UE 资产。
- 按明确标准完成单人和多人验证。
- 以一个功能或小阶段为单位提交 Git，不为无关细节消耗主要时间。
- 小目标验证通过后，Codex 可主动暂存本目标改动；不频繁 push，push 由用户收口或在稳定里程碑获得确认后执行。

## 文档减负规则

- `Current_Phase.md` 是当前状态、下一步和待确认问题的唯一入口，不再维护独立 Pending 文件。
- `Current_Code_Design.md` 只服务于即将实施的代码设计；没有代码任务时保持简短。
- `Current_UE_Manual_Steps.md` 每次覆盖，不积累历史操作。
- Prompt、Report、Review 只为实际实施任务创建。
- 顶层路线只在阶段边界变化时更新。
- 历史资料默认不读；需要论证时通过索引定向读取。

## UE 人工清单规则

- 清单开头必须先说明会决定操作结果的关键机制，例如动画是否为 Additive、资产依赖哪套 Skeleton、Montage 需要哪个 Slot。不能只给接线步骤而省略前提。
- 正文只按 `新增 / 修改 / 删除 / 验证` 描述实际需要用户执行的动作，并给出准确资产名、节点名、目标引脚和值。
- 用户于2026-09-09明确要求：凡需搜索、拖入或替换UE资产，必须在该操作步骤中写出可直接复制的完整资产名，单独放在代码块中。先核对工作区实际资产，不能凭记忆补名称。按用户随后补充，名称足以唯一定位时省略/Game资源路径；仅在同名歧义、需区分资源来源或其他确有必要的情况下补充准确路径，不重复堆叠路径说明。
- 每个状态或操作段独立列明资产名、节点类型、源输出→目标引脚，以及Loop Animation、Play Rate、Alpha等适用参数；不以“普通Idle”“冲刺动画”“同上换成另一动作”等简称代替具体操作。避免要求用户在前文中自行推断要拖入哪个资产。
- 用户不会擅自修改清单之外的内容，因此不重复罗列大量“保持不变”或“不要修改”。只有相邻设置确实容易误操作并会破坏当前结果时，才给一条简短警告。
- 验证先给最小检查，再给完整检查；每项都明确可观察结果，不重复已经完成的旧阶段操作。

## 实施和审查硬规则

- 不在计划批准前擅自写大范围代码。
- 不覆盖用户或其他代理已有改动。
- UE 资产实例按其父类/资产类型使用前缀；`UDataAsset` 与 `UPrimaryDataAsset` 的实例统一使用 `DA_`，不能因为业务名称是 AbilitySet 就改用 `AS_`。
- 新增业务 C++ 文件时，模块内必须使用 `Public` 与 `Private` 分层：`.h` 放入 `Public`，`.cpp` 放入 `Private`；两侧按相同领域建立对称目录，例如 `Public/AbilitySystem/...` 对应 `Private/AbilitySystem/...`。
- 不为只有 `.cpp` 或只有 `.h` 的领域强行创建空目录，但一旦两侧都存在该领域文件，目录层级和命名必须一致。
- 关键代码写学习型注释：既说明做什么，也说明为什么归属在这里；长篇设计理由进入 Markdown。
- 子代理不能自行扩大范围、批量修改 UE 资产、创建 Tag/Release 或清理工作区。
- 不能把“编译成功”当作“玩法验证成功”，也不能把 MCP 返回成功当作 UE 资产完成。
- 通过 Python、MCP 或命令行写入 UE 二进制资产时，必须区分可见属性与编辑器生成的派生/编译数据。保存成功、依赖存在和类可加载都不足以证明资产可运行；需要全新 UE 进程冷加载并直接求值，随后再做最小 PIE 验证。
- 对缺少可靠原生构建接口的少量复杂资产，优先下发精确人工迁移/配置步骤，由用户在 UE 编辑器中完成。不得为节省一次人工操作而采用未经冷加载验证的脚本资产生成路径。
- 涉及网络的能力必须说明 Authority、Owning Client、Simulated Proxy 分别观察什么。
- 发现旧项目做法不适合 Apecox 时，保留历史但重新论证，不为兼容旧实现牺牲新项目边界。

## 子代理调度规则

- 主代理保有架构、任务拆分、最终文件审查、构建验证和 Git 收口责任，不能把最终判断转交给子代理。
- 子代理 Prompt 必须包含目标、允许修改范围、禁止事项、完成条件、验证方式和需回报的文件列表。
- 代码任务优先按互不重叠的文件范围拆分；同一文件不能交给多个子代理并发修改。
- 子代理不得自行执行 `git add`、`commit`、`push`、重置或清理工作区，除非用户对该次操作另行明确授权。
- 可复用的角色约束保留在本文件；每次任务的具体 Prompt 保留在当前任务执行记录中，只把长期有效的设计结论写入项目文档。
- 用户只负责必须在 UE 编辑器中完成的资产配置、视觉判断和 PIE 体验验证，不承担代理之间的 Prompt 转发。
